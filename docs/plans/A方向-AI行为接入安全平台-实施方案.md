# A 方向实施方案：把 AI 工具行为接入公司安全平台

> 配套原型：`docs/prototype/ai-soc/index.html`（单文件，浏览器直接打开）
> 本文只给方案，**不修改任何现有代码**。所有引用的文件、函数、字段均来自当前仓库实际内容。

---

## 0. 一句话结论

当前产品已经能把 AI 工具的高危操作**在本地拦住**并留下**防篡改证据**，但它是一个"孤岛"：
证据出不了这台机器，告警到不了安全团队，处置动作回不到终端。
A 方向要做的只有一件事——**在这座孤岛和公司安全平台之间架一条受控的单向管道，并把零散告警合并成可处置的事件**。

一句话对外表述：

> 把"人"的行为审计扩展到"AI 智能体"，让每一次 AI 代你执行的操作，都能被看见、被分级、被关联、被处置。

## 1. 为什么这条路径能拿分（评审视角）

### 1.1 竞品都在云侧，我们在端点侧

| 赛道玩家 | 做法 | 我们的差异 |
| --- | --- | --- |
| MCP Gateway（TrueFoundry / Obot / Akto 等） | 代理所有 MCP 调用，在网关侧鉴权与审计 | 网关只能看到"经过网关"的调用；本地 CLI、IDE 插件、直接调模型 API 的流量它看不见 |
| AI-DLP 厂商 | 在出口做内容识别 | 只能看到"已经发出去了"的内容；拦不住已经落盘的密钥 |
| 我们的位置 | **执行前钩子 + 端点日志链** | 在工具真正动手之前判定，且证据可验真 |

**答辩时的一句话**："网关解决的是'进不来'，我们解决的是'拦得住、说得清'。"

### 1.2 有真实事故可对标

- **PocketOS 删库（2026-04）**：一次 Railway API 调用，9 秒删掉生产库和备份。当前 `evaluate()` 的 8 条规则**完全覆盖不到**这类"云平台 API 删除"操作。
- **DataTalks.Club（2026-03）**：Claude Code 执行 `terraform` 清空两年半数据。`terraform destroy` 同样不在规则里。
- **Replit（2025-07）**：代码冻结窗口期删生产库。这类"时间窗口内的违规写操作"需要**上下文感知**，单条命令正则做不到。

这三个案例的共同点：**不是恶意攻击，是 AI 按字面理解执行了破坏性动作**。传统安全设备对"合法账号、合法凭证、合法 API"的破坏性调用几乎没有防御。这正是 A 方向的价值锚点。

### 1.3 与公司三条产品线天然咬合

| 公司能力 | 我们的接入点 | 收益 |
| --- | --- | --- |
| 日志分析 / 告警合并 | `events.jsonl` → 统一事件格式 → Syslog/HTTP | 平台第一次有了"AI 智能体"这个日志源 |
| 数据安全 / 分类分级 | 本地对路径与内容做分级，只上报级别与哈希 | 分级结果直接进入平台的资产视图 |
| 用户异常行为分析（UEBA） | 新增"AI 行为基线"维度 | 从"人做了什么"扩展到"人指挥 AI 做了什么" |

## 2. 现状盘点：哪些能用，哪些必须补

### 2.1 已经能用的（真实实现，可直接作为方案地基）

| 能力 | 代码位置 | 可用于 A 方向的部分 |
| --- | --- | --- |
| 执行前判定 | `electron/security/guard-protocol.ts` `decide()` | 决策结果即事件源，无需二次判断 |
| 统一入参归一 | `summarizePayload()` | 已抹平 Codex/Claude/ZCode/DSH 与 OpenCode 两种方言，**这就是天然的归一化层** |
| 防篡改日志 | `logDecision()` | 每行 `prev` + `hash`，SHA-256 链，跨进程文件锁，`0600`，8MB 轮转 |
| 链完整性校验 | `timeline.ts` `verifyChain()` | 外送时可附带链状态，平台侧能判断"这份证据有没有被动过" |
| 任意事件写入 | `center.ts` `record(src, partial, tool)` | 新增事件类型不用改核心，直接 `record()` |
| 统计聚合 | `timeline.ts` `stats()` | `byDay / byTool / byRule / actions` 可直接作为上报的桶 |
| 回溯扫描 | `securityRetroScan` | 补历史数据，让平台侧第一天就有基线 |

**关键结论**：不需要重写采集层。`summarizePayload()` + `decide()` + `logDecision()` 三级已经构成了"采集—判定—落证"的完整链路，A 方向是在末端加"出口"。

### 2.2 必须补的缺口（按阻塞程度排序）

| # | 缺口 | 现状证据 | 影响 |
| --- | --- | --- | --- |
| G1 | **无外送通道** | 全仓库 grep `syslog` / `webhook` / `kafka` / `splunk` 零命中 | 证据出不了机器，平台侧完全看不见 |
| G2 | **事件模型缺字段** | `SecurityEvent` 只有 `id/at/tool/project/sessionId/toolName/operation/ruleId/decision/source/reason` | 没有数据级别、没有用户身份、没有目的地、没有资源对象 |
| G3 | **无事件合并** | 每个 `deny` 都是独立一行 | 平台侧会被同一次会话的多条记录刷屏，告警疲劳 |
| G4 | **规则不覆盖云与数据库** | `evaluate()` 8 + 1 条规则，最重的 `destructive` 只覆盖命令黑名单 | `terraform destroy` / `DROP TABLE` / `kubectl delete` 全部放行 |
| G5 | **无处置回执** | `GuardDecision` 只有 `deny/ask/allow`，没有"已处置"概念 | 平台下发处置动作后，终端没有反馈闭环 |
| G6 | **无行为基线** | `stats()` 只有计数，无对比 | 无法判断"这次和平时不一样" |

G1/G2 是硬阻塞，G3 决定可用性，G4 决定演示效果，G5/G6 决定方案的完整度。

### 3.1 三个设计决定（答辩会被问）

**决定一：为什么外送用"主动推送 + 终端轮询拉取"，而不是平台反向连接终端？**
企业网内终端多在 NAT 后、无固定地址、防火墙禁入站。推送出站 + 轮询拉取是唯一在真实企业网能落地的形态。

**决定二：为什么默认只上报元数据，不上报正文？**
一旦上报命令全文和文件内容，"安全审计"就变成"员工监控"，法律与员工关系风险不可控。默认上报：操作类型、资源标识（路径/库表/域名的**哈希或规范化名**）、数据级别、命中规则、决策、链状态。正文需显式开启，并有独立审批。

**决定三：为什么分级在本地做，而不是传到平台再做？**
正文不出端点是硬约束。本地只算"级别 + 命中规则 ID + 置信度"，平台拿到的是结论不是内容。这与公司现有分类分级能力对齐（平台侧维护规则，终端侧执行判定并上报结果）。

## 4. 数据模型改造（G2）

### 4.1 现有 `SecurityEvent` 的扩展

保持向后兼容：新字段全部 optional，旧记录读取不受影响。建议新增 5 个字段组：

```ts
// src/shared/security.ts —— 建议新增（不删不改现有字段）
export interface SecurityEvent {
  // ... 现有 11 个字段保持不变 ...

  /** 谁在指挥 AI：人类身份 + 设备 + 进程 */
  actor?: {
    user: string;        // 域账号 / 工号（本地取自 OS 登录态，不做额外采集）
    device: string;      // 设备指纹（主机名 + 稳定机器 ID 的哈希）
    agent: string;       // 哪个 AI 工具：codex / claude / opencode / zcode / dsh
    parentPid?: number;  // 便于定位是 IDE 里触发还是终端里触发
  };

  /** 动了什么：资源对象的规范化描述 */
  resource?: {
    kind: "file" | "dir" | "git_ref" | "db_table" | "db_instance"
        | "cloud_resource" | "url" | "mcp_server" | "skill" | "env";
    /** 规范化标识：文件用相对项目根的路径，数据库用 db.schema.table，云资源用 ARN 类标识 */
    id: string;
    /** 上报时用 hash(id + salt) 替代明文，平台侧仍可按同一 salt 做关联 */
    idHash?: string;
    scope: "project" | "home" | "system" | "remote";
  };

  /** 敏感度：本地判定的结论 */
  classification?: {
    level: "L1" | "L2" | "L3" | "L4";   // 公开 / 内部 / 敏感 / 机密
    hits: string[];                      // 命中的分级规则 ID，如 ["id_card", "api_key"]
    confidence: number;                  // 0–1
    method: "path" | "content" | "schema" | "manual";
  };

  /** 数据去哪了：目的地 */
  destination?: {
    kind: "model_api" | "package_registry" | "unknown_host" | "internal";
    host: string;                        // 域名，不含路径与 query
    vendor?: string;                     // 识别出的服务商，如 openai / anthropic / 自建
    firstSeen: boolean;                  // 是否在基线之外首次出现
  };

  /** 处置闭环 */
  receipt?: {
    actionId: string;                    // 平台下发动作的 ID
    action: "rotate_credential" | "disable_mcp" | "revoke_exception"
          | "isolate_session" | "notify_owner" | "false_positive";
    status: "pending" | "done" | "failed" | "unsupported";
    at?: number;
  };
}
```

### 4.2 为什么要 `idHash` 而不是明文路径

平台侧需要按资源做关联（"同一个 `.env` 被三个不同会话读过"），但不该拿到全公司的文件路径清单。
用 `hash(normalizedPath + orgSalt)`：平台能做等值关联，反查需要 salt，而 salt 留在平台侧。这是 DLP 的常规做法，评审问起来有标准答案。

### 4.3 分级规则从哪来

不新建一套。三个来源：
1. **路径规则**：沿用现有 `credential_read` / `protected_path_write` 的路径集合，直接映射到 L4；
2. **内容规则**：复用 `session` 扫描里已有的凭据正则（`sk-` 之类），扩展身份证/银行卡/手机号；
3. **平台下发**：公司分类分级平台把规则包下发给终端（走第 8 节的拉取通道），终端只执行判定。

这样终端不需要维护规则库，也不会与平台结论打架。

## 5. 事件合并（G3）——A 方向最容易被低估的价值点

### 5.1 问题

一次"AI 试图把生产库密钥发到外部"的行为，在现有模型里是 4 条独立记录：
读 `.env.production` → 写入临时文件 → 新增 MCP server → `curl` 到新域名。
平台侧看到的是 4 条中危告警，每一条单独看都"像正常开发"，合并后才是"一条高危事件链"。

### 5.2 合并规则

```
聚合键：actor.device + actor.agent + sessionId
时间窗：首条事件起 15 分钟（滑动续期，上限 60 分钟）
合并条件（满足任一即并入同一事件）：
  R1 同一 sessionId，且窗口内事件数 ≥ 3
  R2 跨数据级别：窗口内出现 L4 读 + 任意出站（destination.firstSeen = true）
  R3 跨对象类型：窗口内出现 ≥ 2 类 resource.kind 且含 file + (url | cloud_resource | mcp_server)
  R4 规则升级：窗口内出现 deny，且其后有同一 session 的 allow（说明绕过尝试）

事件定级（取最高，且只升不降）：
  critical = R2 命中 或 (L4 + deny + 出站)
  high     = R3 命中 或 L4 且 deny
  medium   = R1 命中 且含 L3 以上
  low      = 其余合并结果
```

### 5.3 合并后的价值

- 平台侧告警量下降一个数量级（同会话多步操作收敛为 1）；
- 每条事件自带完整时间轴，调查不用跨系统拼图；
- 事件定级基于**组合关系**而非单点严重度，误报率显著低于逐条规则告警。

这一条建议单独做一页答辩，标题就叫"**为什么 AI 时代的告警必须合并**"。

## 6. 异常行为分析（G6）

### 6.1 基线维度

按 `actor.user × actor.agent` 建基线，每天滚动更新，保留 30 天：

| 维度 | 基线值 | 偏离判定 |
| --- | --- | --- |
| 日均操作数 | P50 | > P95 × 3 |
| 跨项目访问数 | distinct project | 首次出现 | 
| 新目的地域名 | distinct destination.host | 首次出现即标记 `firstSeen` |
| L4 资源访问次数 | count | 由 0 变为 > 0 |
| 夜间操作占比 | 22:00–07:00 | 由 < 5% 变为 > 30% |
| 新装 MCP / Skill | count | 首次出现 |
| deny 触发率 | deny / total | > 10% |

### 6.2 三个最有说服力的检测场景

1. **凭据收割链**：同一会话内，先读 L4 文件 → 再发起首次外部连接。传统设备两个动作都合法。
2. **静默扩散**：某 AI 工具在 1 小时内遍历 20 个以上项目的配置文件。人类不会这么做，Agent 会。
3. **夜间自动化**：非工作时段，"人不在但 Agent 在跑"的批量操作。

### 6.3 不要做的事

不做"AI 意图识别"、不做大模型判风险。原因：不可解释、不可复现、答辩时无法证明准确率。
用**确定性规则 + 统计偏离**，每个结论都能追溯到具体的几条事件。

## 7. 规则补强（G4）

在 `evaluate()` 里新增 4 组规则（现有 8 + 1 条不动）：

| 规则 ID | 级别 | 匹配 | 建议动作 |
| --- | --- | --- | --- |
| `infra_destroy` | high | `terraform destroy`、`terraform apply -auto-approve`、`pulumi destroy` | deny |
| `db_destroy` | high | `DROP DATABASE\|TABLE`、`TRUNCATE`、`DELETE FROM` 无 `WHERE`、`redis-cli FLUSHALL` | deny |
| `cloud_delete` | high | `kubectl delete`、`aws * delete-*`、`gcloud * delete`、`aliyun * Delete*` | ask |
| `prod_write` | medium | 命令或路径含 `prod`/`production`/`--env=prod` 且为写操作 | ask |

### 7.1 实现要点（不改架构，只在 `decide()` 内加分支）

- `destructive` 现在是命令黑名单字符串匹配，新增规则沿用同一形态即可，无需引入解析器；
- `prod_write` 需要"写操作 + 生产标识"两个条件同时成立，建议做成独立函数 `looksLikeProductionTarget(input)`，便于单独测试；
- 每条新规则必须配 3 个用例：正例命中、反例放行、边界（如 `terraform plan` 必须放行）。

### 7.2 演示价值

`terraform destroy` 被拦下的那一刻，比任何 PPT 都有说服力——因为评委知道现实中真出过这事。

## 8. 外送通道（G1）

### 8.1 三种形态，按客户环境选

| 形态 | 适用 | 实现难度 |
| --- | --- | --- |
| Syslog RFC5424 over TLS（UDP 可选） | 已有 SIEM / 日志平台的企业 | 低 |
| HTTPS POST NDJSON（批量 100 条 / 5 秒） | 现代日志接入网关 | 低 |
| 本地文件 + 采集器（写 NDJSON 到指定目录） | 客户已有 Filebeat/Fluent Bit | 最低，推荐首发 |

**首发建议第三种**：不动网络、不改防火墙、不引入新协议，客户装个采集器就接上了。这是最容易过企业安全评审的形态。

### 8.2 必做的工程约束

1. **背压与缓冲**：网络断了不能阻塞钩子。本地环形缓冲上限（如 200MB / 20 万条），超限丢最旧并记录丢弃计数（丢弃本身也是一条事件）。
2. **钩子不能等**：外送在独立进程/线程，钩子只做"写入本地队列 + 立即返回"。当前 `guard-entry.ts` 是 fail-open 设计，外送阻塞会直接拖慢所有 AI 工具，这是不可接受的。
3. **幂等**：每条事件带 `id`，网关侧按 `id` 去重。重试不产生重复告警。
4. **链状态随行**：批次头带 `chainHead`、`chainValid`，平台可判断这段证据是否完整。这是对抗"改日志再上报"的关键。
5. **可关闭**：企业未采购时，默认关闭外送，本地功能完全不受影响。

### 8.3 配置面

```
外送开关（默认关）
目标类型：文件目录 / Syslog / HTTPS
字段白名单：勾选哪些字段出端（分级、目的地、命中等默认开；命令全文默认关）
采样率：高危 100%，中低危可配置
保留期联动：外送成功后本地是否缩短保留
```

## 9. 处置闭环（G5）

### 9.1 四个动作，从轻到重

| 动作 | 效果 | 风险 |
| --- | --- | --- |
| 通知负责人 | 企业微信/邮件推送事件摘要 | 无 |
| 撤销项目例外 | 清掉 `exceptions[]` 里对应条目，规则立刻恢复生效 | 低，可恢复 |
| 停用 MCP / Skill | 从配置中移除对应条目 | 中，影响该员工工作 |
| 隔离会话 | 该 `sessionId` 后续操作全部转 `ask` | 中，需要人能介入 |

### 9.2 回执怎么回来

用第 8 节的拉取通道：终端每 5 分钟 `GET /policy/actions?device=xxx`，拿到待执行动作 → 执行 → `POST /receipt`。
**不做反向推送**：企业网入站不可达，且反向连接会让终端暴露监听端口，是安全评审的雷区。

### 9.3 必须有的"误报"路径

任何自动处置都要有一键误报。误报反馈要回传到平台，用于调整规则阈值。
没有误报通道的自动化处置，在企业里活不过一个月——这句话答辩时讲出来，评委会认为你懂落地。

## 10. 隐私与合规

| 项 | 做法 |
| --- | --- |
| 数据最小化 | 默认只出元数据；命令全文、文件内容需显式开启 |
| 员工知情 | 首次启动明确告知"AI 操作会被审计"，并提供查看自己记录的入口 |
| 本地优先 | 判定全在本地，外送是可选能力，可完全关闭 |
| 标识符处理 | 路径与资源 ID 用加盐哈希出端，salt 由平台持有 |
| 保留期 | 本地默认 7 天（现状），平台侧按公司策略 |
| 依据 | 《个人信息保护法》最小必要原则；《生成式人工智能服务管理暂行办法》对生成内容的可追溯要求；《数据安全法》分类分级义务 |

**答辩要点**：这套设计不是"监控员工用 AI"，而是"给 AI 装行车记录仪"。区分点在于——记录的是**AI 代你执行的动作**，不是你的聊天内容。

## 11. 分期落地

### P0（1–2 周，能演示的最小闭环）

1. `SecurityEvent` 加 `actor` / `resource` / `classification` 三组字段（optional，向后兼容）；
2. `logDecision()` 落盘时填充这三组；
3. 新增 `exporter` 模块，只做"NDJSON 写目录"一种形态 + 本地队列 + 丢弃计数；
4. 新增 2 条规则：`infra_destroy`、`db_destroy`；
5. 安全中心加一页"外送状态"：队列长度、最近成功时间、丢弃计数。

**验收**：跑一次自检载荷 → `events.jsonl` 有新字段 → 目标目录出现 NDJSON → 断网后队列增长、恢复后补发。

### P1（2–4 周，事件合并 + 处置回执）

6. 事件合并引擎（第 5 节规则），输出 `SecurityIncident` 聚合对象；
7. 时间线视图增加"按事件聚合"视图（原型已给出交互）；
8. 拉取通道 + 4 个处置动作 + 回执上报；
9. 误报标记与回传。

### P2（1–2 月，基线 + 平台对齐）

10. 行为基线计算（第 6 节）；
11. 分级规则包下发；
12. 与公司分类分级平台字段对齐（这一步必须平台侧配合，不能自己造标准）。

## 12. 验收标准（每条都要能现场复现）

| 能力 | 验收方式 | 失败边界（要主动说明） |
| --- | --- | --- |
| 字段扩展 | 查 `events.jsonl` 新字段存在且旧记录仍可读 | 旧版本客户端读新记录会忽略未知字段 |
| 外送 | 断网 → 队列增长 → 恢复 → 补发成功，`id` 无重复 | 超过缓冲上限会丢弃最旧，丢弃数可查 |
| 链状态 | 手工改一行 → `chainValid: false` 随批次上报 | 只能证明"本地这段没被动过"，不能证明平台侧未被改 |
| 规则补强 | 4 条规则各 3 个用例（正/反/边界） | 基于文本匹配，混淆写法（如变量拼接）能绕过 |
| 事件合并 | 构造 4 步会话 → 合并为 1 条 critical | 跨设备、跨会话不合并，可能漏关联 |
| 处置回执 | 平台下发撤销例外 → 终端生效 → 回执 done | 终端离线时动作挂起，最长 24h 过期 |

**每一行"失败边界"都要在答辩时主动讲。** 主动划边界的团队，评委才信你说的能力。

---

## 13. 明确不做（写进文档，避免评委追问时被动）

1. 不做系统级 EDR 能力（不注入进程、不拦系统调用）；
2. 不覆盖浏览器里直接用网页版 AI 的场景（钩子机制不适用）；
3. 不做模型侧的内容审核；
4. 不做"AI 意图识别"，不引入大模型判风险；
5. 不做终端反向监听，不接受平台主动连入；
6. 不改现有 8 条规则的语义，只做增量。

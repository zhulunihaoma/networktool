# 任务接续全量识别与上下文完整性改造方案

日期：2026-10-21。状态：本机可验证来源的索引与流式上下文改造已落地；未验证工具和缺失原件尚未满足全覆盖条件。依据：本机只读索引核查、现有适配器源码、OpenCode 隔离数据库副本实验和边界样本复现。

## 1. 交付目标与“全部”的定义

目标不是增加几个兼容正则，而是对每个工具建立可核验的项目、会话和上下文清单，能说明每一条来源记录去了哪里。

- **全部工具**：当前 8 种可读来源全部升级；工具清单中发现的其他安装实例也必须列出读取能力，逐个补齐适配器。VS Code / GitHub Copilot、Gemini CLI、Cursor、Windsurf、Trae 等当前仅可作接力目标的工具，不得计入“已完整覆盖”。产品注册表新增工具时必须同时登记历史读取能力与验证状态。
- **全部项目**：读取原生项目登记和工作区关系，保留空项目、自定义名称、多目录项目、工作树及历史目录。不能继续用“最近读到的聊天目录”代替原生项目清单。仅有历史目录而没有原生项目登记时明确展示为历史目录。
- **全部对话**：枚举已授权数据源中仍有记录的活动、归档、分支、子会话、自动化、草稿及空白会话；分类展示，不因当前接力流程不适用而在索引时丢弃。已删除标记与磁盘残留分别记录，不能把残留直接恢复成活动会话。
- **全部上下文**：保留来源实际保存且可访问的消息、工具调用及结果、附件引用及可读取原件、待办、摘要与压缩事件、分支与父子关系、历史文件变更及快照引用。顺序和来源可追溯。
- **可证明的完成条件**：源项目、会话 ID 集合与识别结果逐项对账，选定范围内的上下文全部读取并校验；缺失项为零、没有未知版本或未完成分页，才能标记完整。

未保存、已永久删除、仅存在于未连接远端、未开放读取接口或无法解密的数据无法凭空恢复。此类情况必须登记具体缺口和补齐路径，不能显示成“没有对话”或“全部读取完成”。来源未保存的内部状态不能通过推测生成。会话关联当前文件路径不等于保存了当时文件内容。

这些数量仅是当时本机快照，不能作为未来固定验收数量；验收必须使用同一次快照的原生记录 ID 集合。

另一个已确认问题：`HandoffImport` 目前以单个 transcript 为核心，8 MB、5000 条消息、12 万字符限制分布在读取和接力生成路径中。它不适合作为全量上下文存储模型。

## 3. 总体修改结构

### 3.1 将安装发现、历史发现和覆盖验证分开

保留现有安装发现，新增来源实例清单：工具、安装渠道、profile、引擎、主机、实际数据根、存储版本、可读取内容类型、验证状态。默认目录、实际配置声明的自定义目录和用户补充目录都进入该清单。目录不存在、没有权限、仅远端可用、版本不支持、来源为空必须是不同状态。

`handoff-tools.ts` 与各适配器使用同一个 `discoverStores()`，避免出现“能读取 state_N，但发现阶段只找 state_5”的两套规则。不能只凭一个目录或数据库存在就声明完整支持。

数据根内的数据库、日志、附件以只读方式访问；不为发现历史启动原任务、执行历史命令、迁移原数据库或调用模型。若原生官方读取服务不可避免地写入其运行状态，需明确区分它与只读文件适配，不能继续统称零写入。

### 3.2 建立持久化本地索引

新增统一索引服务，独立保存来源实例、项目、项目根、会话、会话关系、上下文事件定位、附件定位及对账结果。采用分批扫描、事务提交、扫描检查点和增量更新。

- 项目与会话分别建立索引，不从当前显示的会话页反推项目。
- UI 每页 50 条只影响显示，不限制索引规模或全局搜索范围。
- 去掉 30/5000 条作为全量枚举终点的做法。单批仍有资源预算，但到达预算要保存续扫位置，状态保持未完成。
- 全局搜索至少覆盖完整标题、ID、项目、目录；正文搜索使用已建立的全文索引，并显示正文索引进度，不能将未索引部分当作无匹配。
- 新增/改名/归档/删除/移动项目均增量反映。无可靠变更信号时重新校验，而不是仅依赖 mtime。

来源会话键使用 `来源实例 ID + 原生会话 ID`；不同账号、profile、主机或引擎不能因 ID 相同而互相覆盖。原生 ID 作为不透明字符串处理，限制长度和控制字符，但不再用某个历史前缀决定它是否存在。ID 不直接拼接文件路径，文件定位必须来自经校验的原生关联。

同一存储的新旧表、续写日志和备份是否为同一会话，依据来源身份、原生关联和内容版本判定；冲突保留来源证据，不盲目“最后更新时间最大者获胜”。项目归属优先使用原生关联，路径只作后备；保留多根、别名、移动前目录及歧义。区分 `/var` 别名、真实路径与工作树，不盲目将所有路径转小写。

### 3.3 统一适配器契约

新增版本化协议，至少包含：

```ts
interface HistoryAdapter {
  discoverStores(): Promise<SourceStore[]>;
  inspectStore(store: SourceStore): Promise<StoreCapabilities>;
  scanProjects(store: SourceStore, checkpoint?: string): AsyncIterable<ProjectBatch>;
  scanSessions(store: SourceStore, checkpoint?: string): AsyncIterable<SessionBatch>;
  readContext(session: SessionRef, checkpoint?: string): AsyncIterable<ContextBatch>;
  readAttachment(ref: AttachmentRef): AsyncIterable<Uint8Array>;
  reconcile(snapshot: SourceSnapshot): Promise<CoverageReport>;
}
```

接口需携带 sourceRevision、schemaVersion、snapshotId、nextCheckpoint、exhausted、warnings、未知记录类型和可重试错误。发现、索引、正文、附件分别记录完整性；不能用一个 readable 布尔值代替。

数据库使用只读事务读取 WAL 中已提交记录；日志按固定文件版本和偏移读取。跨库/API/日志无法共享事务时记录各自版本与读取水位，前后复查变化，必要时重试。正在增长的会话标明“完整至某条已提交事件”，未完成写入的尾部不得忽略后宣称全量完成。

## 5. 上下文模型与长对话处理

将目前单个 transcript 改为有来源引用的结构化事件集合：

| 内容 | 必须保存的信息 |
| --- | --- |
| 消息 | 原生 ID、角色、内容块、原生顺序、时间、来源版本、编辑/撤回/分支关系 |
| 工具 | 调用 ID、名称、参数、结果、错误、执行状态及输出截断标记；区分记录完成与实际效果验证 |
| 附件 | 对应消息、原始引用、类型、文件名、大小、可用性、内容哈希及原件定位；大文件分块读取 |
| 压缩与摘要 | 压缩边界、保留的摘要、原始历史是否仍可读；不得将摘要等同于原始全文 |
| 任务与文件历史 | 待办、状态、父子会话、补丁、检查点/快照引用及实际可取得内容；当前磁盘文件与历史版本分别标明 |
| 其他原生事件 | 保留原类型和可访问原始记录引用；未知格式计入待适配，不能静默跳过后标完整 |

对于原工具实际提供的可导出上下文及摘要保留原始类型；不可读取的内部状态只记录能力边界，不生成补全内容。接力时仍将所有历史当作引用数据，不能把历史指令、工具参数或命令重新执行。

识别阶段全量建元数据索引，正文按会话读取或后台逐会话校验。新增“校验全部上下文”任务，遍历所有会话到最终分页并核验每个附件引用，支持暂停、取消和续扫。没有完成这项校验前，只能宣称索引完整，不能宣称所有上下文完整。

**明确取消 8 MB 上下文限制**：所有来源适配器及公共调用链，不再因为单个会话、单条消息、历史文件、解压后正文或整份接力包超过 8 MB 而拒绝读取、跳过索引、截断内容或拒绝归档/导出。不能仅将 8 MB 调大为另一个固定总量上限，也不能通过只保留摘要绕过限制。5000 条消息、12 万字符同样不再作为来源读取和归档的总量限制。

实现改为数据库分页、JSONL 增量解析、解压输出分块、正文块索引、附件流和可续传检查点。覆盖文件读取、CLI 输出采集、RPC 历史分页、上下文归档、IPC 传输和接力包导出整条链路，不能只删除 `HANDOFF_LIMITS.bytes`，却留下 `maxBuffer`、累计响应字节或解压输出总量等价限制。单条消息或单个事件本身超过 8 MB 时也应通过流式解析和落盘处理，不要求整条内容先装入内存。

单批读取、内存占用、并发数和处理时间仍设资源预算，但它们仅决定分块、背压及续读方式，不能成为会话的总量门槛。压缩历史同时校验格式与进度，解压异常明确报错；任务取消、进程重启或磁盘不足时保存检查点并标记未完成，恢复后继续，不将部分结果冒充完整。全量处理能力以实际可用存储及来源可读取能力为边界。

**读取归档和交给目标 AI 分开**：大对话可以全量浏览和导出为包含 manifest、分块记录、附件及哈希的接力包。目标 AI 的输入容量不足时，提供分批接续、附件包和用户选定范围；显示已携带/未携带的事件区间。摘要为派生产物，不替代原件，不能把有损摘要称作完整上下文。原始来源引用与对外脱敏副本分开记录，脱敏变化可统计。

## 6. 页面修改

- 工具页显示所有已发现实例与各自覆盖状态，不再仅对已支持读取的来源提供存在感。
- 项目列表显示原生项目；历史目录另有标识；空项目可见；保留主机、profile 与多个项目根。
- “全部对话”包含各类别的可索引记录；接力默认可筛主会话，但筛选后的数量不能标成来源全部。
- 主会话树下可展开分支与子会话；归档、自动化、草稿、空白、索引残留、待同步分别可查看。
- 展示项目索引、会话索引、正文、附件四项状态，以及来源记录数、已识别数、缺失数、待校验数。来源无法提供总数时显示未知，不显示虚构百分比。
- 错误需定位到来源实例和记录；单条损坏不让整个工具空白，也不在保留其余结果时隐藏失败项。
- 接力预览按内容类型选择，明确是否携带全文、调用结果、子会话、附件和文件快照；大包下载/复制前能看到实际覆盖范围。

## 7. 完整性对账与发布验收

对账使用同一次稳定来源快照，另写独立原生清单提取器或使用原生导出，不能拿适配器自己的 rows() 当作预期结果。

1. **来源实例**：逐一列出本机已发现的工具、profile、引擎和主机；每一项都有可读来源或明确缺口，未接入项阻止全局“完整”状态。
2. **项目**：比较原生项目 ID 集合、名称、项目根和关联；验证空项目、多目录、改名、移动、嵌套仓库、工作树及同名项目。
3. **会话**：按原生 ID 集合做双向差集，并核查类别；活动、归档、草稿、子会话等分类合计可解释每条源记录。备份去重、遗留目录与删除标记均有依据。
4. **正文**：逐个会话遍历至最终页；核对原生消息/事件 ID、数量、顺序、内容块和关联，不只测最近一条、第一屏或部分样本。检查跨页重叠、重复/失效游标、分支、编辑、压缩前后和运行中增长。
5. **附件及文件历史**：逐项解析引用并校验可取得原件的大小、哈希及归属；缺失、受限、仅有缩略图或历史版本已不存在都必须进入缺口清单。
6. **规模及兼容**：超过 30/50/5000 条会话、超过 5000 条消息/12 万字符的长对话、大附件、多帧压缩、未知事件和 schema 升级；验证扫描可续扫且无假完成。8 MB 取消验收至少覆盖临界值以下、等于临界值、略超临界值、64 MB 和 256 MB 上下文，并覆盖单条消息超过 8 MB、压缩文件小于 8 MB 但解压正文超过 8 MB、CLI/RPC 累计响应超过 8 MB、归档与导出包超过 8 MB；所有情况均逐项核对事件及内容哈希，确认没有跳过、截断或遗漏。增加取消续读、重启恢复、磁盘不足及峰值内存受控验证。
7. **真实 UI**：项目与会话可达、全局搜索命中最旧记录、类别过滤、全部分页、完整正文浏览及接力包内容核对；不同启动目录读取同一来源应得到相同集合。
8. **不改变来源**：记录读取前后业务行及文件版本，确认未启动原任务、未执行变更 API、未更改原生项目/会话；备份副本上的迁移测试不能算对原数据只读访问实测。

对每个来源生成验收包：版本与能力、快照范围、原生清单、识别清单、双向差集、项目关联差异、上下文和附件缺口、失败原因与重试结果。报告默认只导出数量、引用与哈希，不包含私人正文。未知总量或不可访问数据必须显式阻止相应维度的完整声明。

原先 32 项测试通过仅证明已有断言成立。本轮要新增独立脱敏样本回归、长对话测试、来源真实快照对账和真实 Electron UI 验证；只有测试样本通过，不能声称本机所有对话已覆盖。macOS、Windows、Linux 按实际验证结果分别记录，不能用一个平台实测替代所有平台。

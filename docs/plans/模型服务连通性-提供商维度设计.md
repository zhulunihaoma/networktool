# 模型服务连通性：以模型提供商为维度（设计）

版本：0.4.0 · Phase 1 已实施 · Phase 2–4 待做

## 1. 背景与问题

当前网络检查有两个维度，都不能回答开发者工具的真实问题：

| 维度 | 数据 | 实际探测对象 | 缺口 |
| ---- | ---- | ---- | ---- |
| 网页平台目录（`AI_PLATFORMS`，14 个） | chatgpt.com、doubao.com、cursor.com 等 | 消费级**网站首页**（Chromium HEAD） | 代码注释已声明：`not an assertion of each product's full API dependency list`；顺序排查注释：`It is not a model/API health check` |
| 本机工具（`TOOL_PRODUCTS`，22 个） | Codex、Claude Code、opencode、Cursor 等 | 仅本地识别与版本检查 | **没有任何网络依赖映射** |

用户的真实场景是：Claude Code / Codex / opencode 连不上。此时依赖链是：

```
工具 → 路由层（官方直连 / 用户自配中转 / 工具自家后端）→ 模型提供商 API 端点
```

探测 `chatgpt.com` 首页是否可达，不能回答 `api.openai.com` 是否可达。两者经常是两套基础设施，互不充分也不必要。

**结论：网络健康度的第一维度应改为「端点 / 模型提供商」，工具作为投影保留。**

## 2. 设计原则（沿用现有产品纪律）

1. **证据优先、只读、按需采集**：不自动监测，点击才探测；不发送凭据、不读请求正文。
2. **可达 ≠ 功能正常**：端点无凭证探测只证明网络路径，不证明账号有效、对话可用或工具已恢复。现有 `reachable / auth_required / restricted` 语义平移。
3. **端点可核验**：每个端点登记官方文档来源（`source` 字段），未经官方来源核验的端点不启用，与 `AI_PLATFORMS` 的来源纪律一致。
4. **实际端点从配置解析，不从工具身份推断**：工具可配任意 base_url，推断即猜测。

## 3. 数据模型

### 3.1 提供商与端点注册表（新增 `src/shared/providers.ts`）

```ts
export interface ProviderEndpoint {
  id: string;                    // "openai-api" / "ark-volces" / "openrouter"
```

## 4. 探测设计

### 4.1 管线

API 端点探测改用现有分层管线 `runProbe`（DNS → TCP → TLS → HTTP），替代网页目录的 Chromium HEAD 单跳：

- 每条证据沿用现有 `Evidence` 格式与「直连 / 代理路径」分组，`ProviderResult.paths` 复用 `PlatformPath`。
- HTTP 阶段：无 Cookie、无授权头、固定 `User-Agent: NetworkLens/<ver> NetworkCheck`、不跟随重定向、不读响应正文。
- 超时、并发（≤4 worker）、停止丢弃迟到结果、单端点 30 秒限频，全部沿用 `PlatformDoctor` 语义。

### 4.2 未认证响应判定（`classifyProvider`，由 `classifyPlatform` 泛化）

| 观察 | 判定 | 文案要点 |
| ---- | ---- | ---- |
| HTTP 2xx / 3xx | reachable | 网络可达，服务已响应 |
| HTTP 401 / 405 / 404（在 `expectAnon` 内） | auth_required | **网络与 TLS 正常，服务要求认证**——对 API 端点这是最佳可达信号；不证明账号有效 |
| HTTP 403 / 451 | restricted | 平台拒绝（地区 / 企业网络 / WAF），建议核对实际出口 |
| HTTP 429 / 5xx | busy | 服务限流或异常，不证明全球故障 |
| TLS 成功但无 HTTP | network_reachable（部分） | 链路通、入口未响应，不当作断网 |
| DNS / TCP / TLS 失败 | network_error | 按失败阶段出建议（沿用现有文案模式） |
| 未在 `expectAnon` 内的其他状态 | reachable，摘要注明「返回未登记状态 HTTP n」 | 原始状态永远进证据，不被分类吞掉 |

与网页目录的关键差异：对 API 端点，**401 是预期且良好的响应**；判定逻辑按端点的 `expectAnon` 白名单解释，而不是按网站语义。

### 4.3 实际端点解析（Phase 3，新增能力，需单独评审）

工具的实际 base_url 从本机配置**只读**解析：

- 路径白名单制：每工具登记候选配置文件（如 `~/.claude/settings.json`、`opencode.json`、工具自身配置目录），逐个 try-read，失败记为「无法读取」，不当作无配置。
- 只提取 base_url 类字段；**永不读取、复制、展示 API key / token 字段**；解析命中后在 UI 标注来源（文件路径 + 字段名）。
- 解析结果按 host 归入注册表端点；不在注册表的 host 归为「用户自配中转」，单独成组，探测语义相同但文案声明「无法核验该中转的归属与策略」。
- 不读取其他进程的环境变量；shell rc 文件不解析（脆弱且越界），在「尚未确认」中说明。

## 5. UI 组织：左侧两个一级 Tab

首页（现 `ToolHome`）拆分为侧边栏两个并列的一级入口，分别承载「本机有什么」和「外面通不通」两个问题：

```
侧边栏
├─ 应用                    ← 原 ToolHome 的工具部分
├─ API 提供商              ← 新增，连通性看板
├─ 文件策略与审计           （不变）
├─ 诊断历史                （不变）
├─ 高级排查（诊断工作区 / 应用联网 / 会话对比）（不变）
└─ 偏好设置                （不变）
```

### 5.1 「应用」Tab（本机视角）

- 已安装工具识别、版本与更新检查（现有 `InstalledTools` 能力，不变）。
- 工具卡投影（Phase 2）：每张工具卡显示「默认依赖 → 提供商端点 · 最近探测结果 / 未探测」；配置解析出实际端点后（Phase 3）改显实际端点及来源。探测结果从提供商看板共享，不在此重复发起。
- 工具级诊断入口保留（沿用现有 wizard + `toolContext` 冻结）。

### 5.2 「API 提供商」Tab（网络视角，新首页默认 tab）

- **模型服务连通性看板**：按提供商分组的端点卡片（官方 API / 聚合中转 / 工具后端分组展示），状态沿用现有徽章语义；「开始检查」手动触发，无自动监测。
- **用户自配中转**分组（Phase 3）：配置解析命中的注册表外 host 单列，文案声明无法核验归属。
- **顺序排查入口**（Phase 4）：从提供商卡片发起对该端点的顺序排查，第 4 步探测对象从网页入口换成实际端点。
- **网页平台目录**：折叠在整个 tab 底部，降级为「网页入口辅助检查」，文案保持「公开入口不代表 AI 请求路径」。

### 5.3 联动关系

- 两个 tab 共享同一份 `ProviderScan` 状态；应用 tab 只读投影，探测只在提供商 tab 发起（或从工具卡跳转到对应提供商卡片并预选中）。
- 提供商卡片上的异常可一键进入：单端点重测 / 顺序排查 / 打开官方状态页 / 复制结果给 IT（沿用现有动作组）。
- 默认落地 tab 为「API 提供商」：网络健康度是产品主轴；「应用」tab 回答该结果影响本机哪些工具。

## 6. 与现有模块的关系

| 模块 | 变更 |
| ---- | ---- |
| `AI_PLATFORMS` / `scanPlatforms` | 保留，不动；折叠进「API 提供商」tab 底部，定位降级为网页入口辅助检查 |
| `TOOL_PRODUCTS` / 工具识别 / 更新检查 | 不动，归入「应用」tab；新增「默认依赖端点」只读字段（登记来源） |
| 顺序排查（triage） | Phase 4 切换第 4 步探测对象；入口从首页移至提供商卡片 |
| 诊断会话 / 对比会话 | 不变；向导目标可从注册表选择 |
| 证据 / 报告 / 脱敏导出 | 复用；端点结果可并入 IT 反馈文案 |

新增 IPC（白名单，与现有命名对齐）：`providers`、`scan-providers(id?)`、`stop-providers`、`onProviders`；语义与 platforms 组一致。demo 模式（`src/demo.ts`）同步提供演示数据。

## 7. 安全与隐私边界

- 全部探测无凭据、无 Cookie、无请求正文；不执行 PAC 之外的脚本；不修改系统代理 / DNS / 证书。
- 配置解析（Phase 3）是唯一新增的本地读取面：白名单路径、只读、仅提取 base_url 字段、来源明示；key 类字段永不出文件。
- 探测目标只含注册表端点与用户明确输入的目标；注册表外 host 不主动探测（用户自配中转经解析命中后，作为该用户的已确认目标探测）。
- 导出的 IT 反馈内容沿用脱敏纪律：不含账号凭据、内部接口地址、原始代理端点。

## 8. 不做的事

- 不发送认证请求验证 key 有效性；401 不证明账号状态。
- 不验证对话 / 流式生成 / 文件上传能力；端点可达不证明工具功能恢复，仍需用户在工具中复测（沿用「用户声明」机制）。
- 不断言工具与提供商的对应关系未经配置验证；默认映射只标「默认依赖」。
- 不猜测无官方来源的工具后端域名；不将远端 IP 反推域名 / 提供商。
- 不做自动持续监测；保持点击触发的按需采集。

## 9. 验证计划

- `classifyProvider` 单测：401/403/451/429/5xx/未登记状态/TLS-only/各阶段失败/fixture 证据 → 判定与文案（沿用现有 classify 测试模式）。
- 探测管线 e2e：本地 mock HTTPS server 模拟各状态码与超时，验证证据链与 paths 分组。
- 限频 / 停止 / 并发：复用 `PlatformDoctor` 语义测试。
- Phase 3 配置解析：fixture 配置文件（含 key 字段）→ 断言只提取 base_url，key 不出现在任何输出。
- UI 验证：沿用 `docs/validation/` 的截图 + 结果 JSON 流程。

## 10. 分阶段实施

| 阶段 | 内容 | 交付物 |
| ---- | ---- | ---- |
| Phase 1 | `providers.ts` 注册表（首批端点逐条核验来源）+ `classifyProvider` + `ProviderDoctor` + IPC + 首页拆分为「应用 / API 提供商」双 tab，提供商看板落地 | 可手动检查的提供商 tab |
| Phase 2 | 工具「默认依赖端点」字段 + 应用 tab 工具卡投影 + IT 反馈文案并入 | 工具→端点默认映射可见 |
| Phase 3 | 配置只读解析实际 base_url + 自配中转分组 | 按实际端点探测（单独安全评审） |
| Phase 4 | triage 第 4 步切换实际端点（从提供商卡片发起）+ 诊断向导端点候选 | 顺序排查对准真实依赖 |

每阶段独立可发布；Phase 1 不依赖 Phase 3 的解析能力（先按默认端点探测）。

## 11. 本版限制

端点注册表是人工维护的白名单，覆盖常见提供商，不完整；未登记的自建网关只在配置解析命中后作为用户已确认目标出现。探测频率受 30 秒限频约束，结果只代表本次网络路径，不构成 SLA 监控。Phase 3 前，「默认依赖」不等于工具实际使用的端点。
